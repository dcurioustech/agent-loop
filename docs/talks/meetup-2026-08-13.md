## 1. Problem / context

Coding-agent CLIs (Claude Code, Codex, Grok CLI, Gemini CLI, Antigravity's
`agy`) are capable of multi-step, multi-file work — but using one unattended
means either babysitting every step, or trusting a long run blindly with no
checkpoint and no second opinion.

## 2. What agent-loop solves

Adversarial pairing: one CLI plays **developer**, another plays **reviewer**,
gated by a `plan_checkpoints.json` state machine. Per-checkpoint git commits.
Human only reviews/merges at the end. Originally extracted from a Flutter
project's `run_loop.sh`, generalized to be project-agnostic (build/test/lint
commands declared per project, not hardcoded).

## 3. How it works

- `orchestrator.py` — the loop: developer writes → commit → reviewer checks →
  approve or send back with notes (revision loop) → repeat until approved or
  `max-review-attempts` exceeded.
- `state.py` — `plan_checkpoints.json` is the coordination contract: not an
  API or tool-schema, a shared JSON file both CLIs read/write directly.
- `plan_init.py` — `agent-loop init` generates that plan file from a
  plain-English feature description (or a Markdown file), writing it only if
  the CLI's output parses as JSON *and* passes normal schema validation.
- `providers/` — one thin wrapper per coding-agent CLI (registry + `@register`
  pattern), each just shells out to the real binary.
- Safety net: protected-branch refusal, dirty-worktree refusal, opt-in danger
  gate (`ALLOW_DANGEROUS_<PROVIDER>=1`), hard halt after max review attempts,
  and never auto-merges.
- `audit.py` + run logs — logs live in `logs/` at the repo root by default and
  are **git-committed audit artifacts**, not scratch files. Alongside raw agent
  output they carry structured one-line JSON events (`AGENT_TRACE`,
  `REVIEW_COMMENT`, `APPROVAL_COMMENT`, `COMMIT_STATEMENT`, `RUN_OUTCOME`).
  `--audit-level` (`full` / `redacted` / `off`, **default `off`**) controls how
  much raw agent content reaches that permanent record.

## 4. Install & usage

```
pipx install -e <path-to-clone>          # not on PyPI yet — clone first
agent-loop init "add a --top N flag"      # generate plan_checkpoints.json
agent-loop validate                        # schema-check + CLI preflight
agent-loop status                           # one-line summary per checkpoint
agent-loop run                               # developer=claude, reviewer=codex (defaults)
agent-loop run --audit-level full             # log agent output, not just events
```

Danger gates are per-provider and off by default:

```
ALLOW_DANGEROUS_CLAUDE=1   # claude --dangerously-skip-permissions
ALLOW_DANGEROUS_CODEX=1    # codex exec --dangerously-bypass-approvals-and-sandbox
```

Full runbook with exact commands and verified expected output:

Sequence: `validate`/`status` (+ optional `init`) → protected-branch refusal →
danger-gate refusal → dirty-worktree refusal → real developer/reviewer run

`agent-loop status` close (no auto-merge).

## 6. Failure-mode & audit-trail recap

Name the four safety behaviors just demoed (branch guard, dirty-worktree
guard, danger-gate opt-in, max-attempts halt), plus: no auto-merge, ever.

Then the audit trail, which is the strongest part of the story: run logs are
**committed to git**, not left in `/tmp`. Each checkpoint commit carries the
log as of that moment and a closing `audit:` commit flushes the tail, so the
record survives even a failed or halted run. Every run emits greppable
one-line JSON events (`AGENT_TRACE`, `REVIEW_COMMENT`, `APPROVAL_COMMENT`,
`COMMIT_STATEMENT`, `RUN_OUTCOME`). And because that record is permanent,
`--audit-level` defaults to `off` — structured events only, no raw agent
output — with `redacted` (best-effort secret-shape scrubbing) and `full` as
explicit opt-ins. Landing line: an unattended loop that is still fully
inspectable afterwards, with a deliberate choice about what becomes permanent.

## 7. Expanding agent-loop

- More providers: Aider, Cursor CLI, OpenHands, a local/Ollama wrapper.
- Checkpoint dependency graph instead of strict linear order.
- Structured tool-calling instead of shared-file coordination (reduce
  reliance on the agent correctly editing the JSON by convention).
- Multi-reviewer / voting (N reviewers must agree before approval).
- Stale-lock detection — known rough edge: a SIGKILLed run leaves the
  lockfile directory behind (no PID/staleness check today).
- CI integration — run as a GitHub Action.
- Cost/token tracking per checkpoint.
- Richer redaction for `--audit-level redacted` — today it's a regex net over
  known secret shapes and explicitly best-effort; project-specific secret
  formats and secrets split across flushed writes can still slip through.
- Machine-readable log output (JSONL) so the structured events can feed a
  dashboard rather than `grep`.

## Appendix: shortcomings found and fixed while prepping this demo

**Fixed:**
- No `LICENSE` file despite `pyproject.toml` declaring MIT → added.
- No `CONTRIBUTING.md` → added.
- `pyproject.toml` `description` was stale (missing Antigravity) → fixed.
- `cli.py`'s `_cmd_run` didn't catch `GitError` — a protected-branch or
  dirty-worktree refusal *inside* `run_loop()` surfaced as a raw Python
  traceback instead of a clean `error: ...` message like every other setup
  failure. Fixed (`GitError` added alongside `InvalidPlanState`), with a
  regression test in `tests/test_cli.py`.

**Known, not fixed (rehearse around / call out live):**
- GitHub repo is private — visibility flip is a manual step.
- Not published to PyPI — install is `pipx install -e <clone>` today.
- Lockfile has no staleness/PID check — a hard-killed run can leave
  `LockHeld` behind for the next `run`.
- No CI / status badge yet — good "first PR from the audience" idea.

**Updated after merging `main` (PRs #5, #6, #9, #10):**
`main` moved substantially after this outline was first drafted, and the demo
materials were re-verified and rewritten against it:
- **`agent-loop init` is new** — plans can now be generated from plain English
  rather than hand-written. Added to the usage section and offered as an
  optional demo beat (it's a single live LLM call with no fallback, so it's
  safer as a slide than a live command).
- **The audit story changed completely.** Logs moved from `/tmp/agent_loop_logs`
  to `logs/` at the repo root and are now *git-committed*, with structured JSON
  events and a new `--audit-level` (`full`/`redacted`/`off`, default `off`).
  The runbook's audit beat was rewritten around `git log` + `grep` of the
  events, and now passes `--audit-level full` explicitly — at the default `off`
  the old "cat the log to see prompts and responses" beat shows nothing.
- The demo scaffold's `.gitignore` no longer ignores `logs/` — ignoring it
  would have hidden the very artifacts the demo is about.
- `require_clean_worktree` now tolerates changes under the log directory; the
  `scratch.txt` dirty-worktree demo still fires correctly (verified).

**Non-obvious mechanics worth knowing before demoing:**
- The protected-branch check looks at the `"branch"` field *declared in
  `plan_checkpoints.json`*, not whatever branch is currently checked out in
  git. A plan file that names a non-`main` branch will happily
  auto-checkout/create that branch even if you're sitting on `main` when you
  run it.
- Check order for `agent-loop run` is: provider preflight (binary on PATH) →
  danger-gate check → lockfile → *then* protected-branch check → dirty-worktree
  check → the loop itself. Demoing the branch/worktree refusals requires the
  danger gate to already be set, or you'll always hit the danger-gate refusal
  first regardless of branch/worktree state.
- `claude --dangerously-skip-permissions` refuses to run under root/sudo —
  irrelevant on a normal laptop, but bit this exact prep session (running in
  a root container).
